# 编写、修改与恢复

只读取当前模式。共同遵循入口的权限、强度、证据与冲突规则。

## CREATE

必需：用户希望复用的能力与成功结果。平台、样例、资产和依赖仅在决定实现时才必需；可从当前环境及明确要求推导合理默认并说明。无法确定能力本身时询问，不编造需求。

执行：提取真实场景 → 定义触发/排除与输入输出 → 选择必要流程和依赖 → 编写最小有效入口与按需资源 → 执行成功、缺输入、边界场景 → 交付源及适用性记录。开放创作保留自由度，脆弱操作才固定步骤。

产物：自包含的 SKILL.md、实际需要的参考/脚本/资产；FULL 另有来源/需求记录和验收证据。无旧版时回归 N/A，原因写“首次创建”；新增执行逻辑属于实现选择，明确区别于用户原始要求。通过条件是需求能在观察到的行为中得到满足，不能只检查章节齐全。

## UPDATE

必需：可读取的既有源和用户要求的改动；先查找当前文件，无法确定对象再询问。确定行为影响和版本范围，系统性优化用 FULL。

执行：保存旧版及哈希 → 建立 CR 和能力基线 → 修改受影响部分 → 记录保留/迁移/条件化/授权变更/删除 → 核对关键约束 → 执行受影响功能及旧行为代表用例 → 更新版本和变更记录。

产物：新版源、可恢复旧版、差异与验证。完整行为合同变化使用主版本；兼容新增使用次版本；不改变行为的修订使用补丁版本。未改软件项目时不更改其独立版本。

通过条件：请求变更已实现，未授权能力变化为零，关键能力有新位置或明确授权的移除理由。保留能力意味着保留语义，可重组和去重；无需机械保留冗余原句。没有能力变化的格式修订可用 LIGHT 并将行为重测记 N/A，必须说明影响分析。安装或外部发布单独按 DEPLOY 合同处理，不能因 UPDATE 偷做。

## RECOVER

必需：目标身份及至少可检查的源/版本/归档线索；先搜索已有工作区、登记目录和历史版本。旧平台包可作为候选来源，但必须标明证据强度。

执行：盘点候选和哈希 → 比较职责、触发、输入、流程、QA、异常与输出 → 按来源证据恢复 → 逐项记录确定、冲突和缺失 → 验证已恢复的部分 → 登记版本和恢复入口。

产物：恢复候选、源清单、能力映射与缺口报告。完整来源不可得时仍可完成审计或恢复草案，完整保真状态 UNVERIFIED/BLOCKED；不把根据经验重写的内容冒充恢复。选择最新版本要有内容与来源依据。无源或权限阻断只停止相应恢复阶段，保留可用成果。完整恢复通过须覆盖全部适用原能力并有实际验证。
